# Photobooth Kiosk

A Flutter Android photobooth for an Android tablet and an ESP32 coin-slot controller over Bluetooth Low Energy (BLE).

## Build and run

Install Flutter, Android Studio, Android SDK 36, and a Java 17-compatible Android toolchain. Open this project root (the folder containing `pubspec.yaml`) in Android Studio, or run these commands from the project root:

```powershell
flutter pub get
flutter run
```

To build a debug APK for installation:

```powershell
flutter build apk --debug
```

The APK is written to `build/app/outputs/flutter-apk/app-debug.apk`. The app requires Android 8.0 (API 26) or newer, camera access, and Bluetooth access. On Android 8–11, Android also requires location permission and may require Location Services enabled to scan for BLE devices. Enable Bluetooth on the tablet and power on the ESP32. Tap the SnapLab logo three times within two seconds on the home or photo-count screen to open admin access. The first visit creates the admin password.

Photos are saved to `Pictures/Photobooth`. The app discovers the ESP32 by its BLE service UUID and connects automatically; no Wi-Fi, pairing screen, or ESP32 URL setting is needed.

### Customer photo downloads by QR

After a photo session, including a free test-mode session, an activated booth uploads the confirmed photo, an animated GIF of the captured sequence, and a moving-photo MP4. The MP4 records each live countdown for its configured 3–5 seconds, then briefly holds the selected framed photo after each shot. Each file gets its own QR code. The confirmed PNG photo is also saved locally and used for printing. If the photo exceeds 18 MB, the app creates a temporary high-quality JPEG upload copy under the server's 20 MB limit; the original photo remains unchanged for local saving and printing. If GIF or MP4 creation fails, the booth reports the issue and still uploads the confirmed photo. Photo, GIF, and MP4 uploads share one five-minute authorization and run sequentially, so the photo QR can appear before the other uploads finish. The app safely follows up to three same-origin HTTPS HTTP 307/308 redirects returned by the authorization route; it refuses cross-origin or insecure redirects. The server verifies the booth's device-specific activation code and issues the upload credential; the app does not contain or store the server signing secret. Test-mode uploads use Hostinger storage and count toward its bandwidth/storage usage. Download links work over the internet for seven days; the server removes expired files when a later upload occurs and refuses expired links. JPEG, PNG, GIF, and MP4 uploads are limited to 20 MB.

One-time Hostinger setup for the owner:

1. In Hostinger File Manager, open the document root for `snaplabbooth.com`. Upload `ganap_common.php`, `pb_auth.php`, `pb_upload.php`, `pb_download.php`, and `pb_cleanup.php` directly into this root; `pb_auth.php` depends on `ganap_common.php` to validate both legacy and feature-enabled activation codes. Their prefixed names avoid replacing your existing website files. For an existing installation, replace `pb_upload.php`, `pb_download.php`, and `pb_cleanup.php` with the updated versions so MP4 uploads, downloads, and expiration cleanup are supported.
2. Upload the `photobooth_private` folder, including its `photobooth_config.php` and `.htaccess`, into the same root. The hosting account must support PHP 8 or newer and the PHP Sodium extension; enable `sodium` for the site's active PHP version in Hostinger's PHP extensions settings, or ask Hostinger support to enable it. The live auth route returns `server_ed25519_support_unavailable` until Sodium is available. Do not replace your website's existing root `.htaccess`.
3. In `photobooth_private/photobooth_config.php`, replace `credential_signing_key` with a new random secret of at least 32 characters, generated on your computer with `php -r "echo bin2hex(random_bytes(32)), PHP_EOL;"`. Keep this secret only on the server; it signs the short-lived upload credentials and must never be added to the app or APK. Keep `activation_public_key` in sync with the public key in `lib/device_activation.dart`, and set `base_url` to `https://snaplabbooth.com`. Photos and the configuration are inside the denied-access `photobooth_private` directory. Deploy this new config and rotate any previous upload token when deploying this version.
4. No per-booth upload settings are required. The app uses `https://snaplabbooth.com/pb_upload` automatically and sends the device-specific activation code to `https://snaplabbooth.com/pb_auth` over HTTPS to request a five-minute credential. These public endpoint URLs intentionally omit `.php` because Hostinger redirects the `.php` form of these routes.
5. In Hostinger hPanel, add a daily cron job that runs `pb_cleanup.php` using the account's PHP command/path. This permanently deletes expired files even when the booth is not uploading new photos.
6. Test with a free test-mode session or a paid session, scan the displayed QR code, and confirm the image downloads. The app keeps its local copy even if online upload fails.

The Hostinger domain must have a valid HTTPS certificate and PHP enabled. Keep `photobooth_private` blocked from direct web access by its `.htaccess` rule and preserve any existing website files and root `.htaccess`. The app continues saving locally if server authorization or upload fails.

### Ganap QRPh payments

Ganap QRPh is currently **disabled** because the booth's fixed session price is ₱20 and Ganap's documented checkout minimum is ₱200. The app hides the customer payment button, disables the Admin toggle, and the server rejects checkout attempts before contacting Ganap. This prevents an accidental ₱200-or-higher charge. Do not enable payments or raise the amount to bypass this protection.

The integration is prepared for Ganap's current `POST https://api.ganap.net/v1/checkout` API, which expresses `amount` in pesos. When Ganap supports the booth's ₱20 price, the client can display a hosted checkout URL, raw QR Ph payload, or QR image returned by Ganap. The server signs the exact JSON request body with HMAC-SHA256, verifies the webhook's `X-Ganap-Signature` against its raw body, accepts only the documented `transaction.paid` event, matches its reference and ₱20 amount to a pending order, and stores payment state in `photobooth_private/ganap_orders.json`. The order file is inside the existing web-denied private directory. The server also verifies the booth's activation code for checkout creation and payment-status requests. No Ganap secret is included in Flutter.

When the provider minimum permits ₱20, configure `ganap_project_uuid`, `ganap_signing_secret`, and `ganap_customer_email` in `photobooth_private/photobooth_config.php`; keep the signing secret private. `ganap_amount` must remain `20` (pesos), matching the booth's fixed price. Ensure Hostinger's PHP cURL and Sodium extensions are enabled and that PHP can write to `photobooth_private`. The private configuration file is excluded from Git; update the live server config separately through Hostinger File Manager without overwriting its existing secrets or activation key.

Upload `ganap_common.php`, `ganap_checkout.php`, `ganap_status.php`, and `ganap_webhook.php` into the `snaplabbooth.com` document root. Set the Ganap Webhook project's endpoint to the extensionless URL `https://snaplabbooth.com/ganap_webhook`, because Hostinger redirects the `.php` form. Keep Ganap payments disabled until the provider's documented minimum supports ₱20 and test mode verifies the webhook payload and confirmation flow.

### PayMongo QR Ph payments

PayMongo uses its dynamic QR Ph Payment Intent flow. Admin can set the QR Ph charge from ₱1 to ₱100,000 in whole pesos; it defaults to ₱20. This setting affects PayMongo QR Ph only—the coin-slot session price remains ₱20. The configured QR amount is sent in pesos and converted to centavos by the server. Both the admin toggle and the server-side `paymongo_enabled` configuration are off by default; checkout and status requests are rejected until an operator deliberately enables the server configuration after testing. Payment is recorded only after the server retrieves the matching Payment Intent directly from PayMongo and verifies its ID, saved amount, currency, and `succeeded` status. The server checks activation codes for checkout and status requests, and API keys are never included in Flutter. The booth hides and rejects online payment while its free test mode is active, so test sessions cannot accidentally create live charges. By default, QR Ph funds go to the server's parent PayMongo account, preserving existing booth behavior. If a Fleet owner has an activated linked child account, that owner's registered booths automatically route new QR Ph payments to that child account instead. Other booths continue using the parent account. This does not change PayMongo's payout setup or timing.

In `photobooth_private/photobooth_config.php`, set `paymongo_public_key` and `paymongo_secret_key` using the PayMongo Developers dashboard, and add `paymongo_enabled => false` until the integration has been verified with test-mode keys. Only after testing, set `paymongo_enabled => true` to accept the configured mode. Public and secret keys must both be test keys or both be live keys. Do not put either key in the app, dashboard, or public web root. Keep both values private and preserve the server's existing configuration when editing it through Hostinger File Manager.

Upload the latest `paymongo_common.php`, `paymongo_checkout.php`, and `paymongo_status.php` into the `snaplabbooth.com` document root. Add the `paymongo_checkout` and `paymongo_status` extensionless rewrite rules from [FLEET_REWRITE_RULES.txt](hostinger/photobooth/FLEET_REWRITE_RULES.txt) to the top of the existing `public_html/.htaccess`; the app calls these routes without `.php`. The server also needs PHP cURL and Sodium, HTTPS, and write access to `photobooth_private`, where pending PayMongo order records are stored. No PayMongo webhook is required for this implementation: the status endpoint polls the authenticated Payment Intent API and checks the exact amount saved with the order before confirming a sale. QR expiry is set to five minutes (within PayMongo's documented 60–9000-second range) to limit abandoned checkouts. Set **PayMongo QR Ph amount** and enable **Allow PayMongo QR Ph payments** in Admin only after deploying the endpoints and testing with PayMongo's test-mode flow. The app uses the API's documented `test_url` simulation in test mode and does not display a test payment QR that could be scanned with real funds.

### Local browser dashboard

PayMongo QR Ph sales are added to the booth's persistent sales ledger only after the server verifies that the Payment Intent for the configured amount has succeeded. Coin-slot sales remain ₱20. When the coin balance reaches the session price, or the QR Ph payment is verified, the customer sees a green confirmation notice stating that payment was accepted and they can start the photo session.

After the app is activated and an admin password is configured, it starts a local dashboard on port `8765`. Open Admin settings on the booth device to see its `http://` address, then open that address in a browser on a device connected to the same trusted Wi-Fi network. Sign in with the existing app admin password. Keep the Photobooth app running in the foreground.

The dashboard is organized into sidebar pages for **Overview**, **Sales**, **Activity log**, **Booth settings**, **Media & branding**, and **Admin capture**; the navigation adapts to narrow browser screens. Overview refreshes live camera, ESP32, credit, session, kiosk, battery/charging, free-storage, voice-guidance, and printer status. Sales shows all-time totals, today's sales, this week's sales, and a graph comparing each of the past seven days. Activity shows up to 50 recent events from the current app run. The local **Booth settings** page lets admins set the coin-slot price (₱1–₱100,000, default ₱20) and the separate PayMongo QR Ph amount (₱1–₱100,000, default ₱20). ESP32 coin credits must map 1:1 to pesos. PayMongo QR Ph can be enabled only when the booth activation includes that feature. Ganap QRPh keeps its existing ₱20 checkout amount and is shown as available only when activation and its minimum-charge requirement allow it. Prices remain the same regardless of photo count or layout. New Ganap QRPh sales are recorded only after the backend verifies a payment notification. Any historical e-wallet-reference sales remain unverified. Sales totals persist on the booth device; older sales recorded before this adjustable-price update are retained without conversion. Recent events are held in memory and are cleared when the app restarts. Settings and Media pages can change operational options, idle-screen media, and custom PNG frames; Ganap checkout QR codes are generated uniquely per transaction. Admin capture can start a photo session and intentionally bypasses payment without counting a sale.

The dashboard is reachable by other devices on the local network and uses unencrypted HTTP. Use it only on a private, trusted Wi-Fi network—not public Wi-Fi—and keep the admin password private. The dashboard restores your login after a browser refresh while its session is valid; sessions expire after 30 minutes of inactivity, and media uploads have size/type limits. Restarting the booth app ends active dashboard sessions. This dashboard is local only and is not available over the internet.

### Online multi-booth monitoring

The fleet site is deployed at `https://snaplabbooth.com/` with a clean URL; use the Hostinger deployment guide below to update its files when releasing fleet changes. The local demo runs at `http://127.0.0.1:8787/pb_fleet.php` and uses synthetic booth data. The deployed fleet service uses a MySQL database via PHP PDO, with schema in [fleet_schema.sql](hostinger/photobooth/fleet_schema.sql). Its foreign keys connect Fleet accounts and device registrations to shared owner identities, and each device's telemetry, settings, commands, and alerts to its registration. It also links password resets and email reports to accounts. It stores owner accounts/password hashes, booth registrations, each booth's latest telemetry/sales snapshot, remote settings, queued commands, and hashed-IP rate-limit records. It does not store photos, activation codes, customer details, local admin passwords, or payment-provider credentials. Configure DB credentials only in the protected server-side `photobooth_config.php`; follow the [Hostinger deployment guide](hostinger/photobooth/FLEET_DEPLOYMENT.txt) to create the database, import the schema, and deploy. Owner registration and administrator/owner login require Cloudflare Turnstile verification; configure its site and secret keys in the protected server config. Once deployed, booth owners can self-register with a unique email and a 12-72 character password. Each owner account sees only devices and sales assigned to that account; the configured administrator password retains fleet-wide access. Register a booth by providing its Device ID and signed activation code. The server verifies the code, assigns the booth to one account, and rejects reports from unregistered booths. Unregistering a booth disables reports while preserving its history for the same owner; only the administrator can arrange an ownership transfer. Email verification and password recovery are not configured, so users must use an email address they control and keep their password safe. The dashboard monitors registered, activated booths over HTTPS and shows last-seen/online status, camera and ESP32 state, battery, and the booth's recorded coin/QR Ph sales. Owners can queue an app restart or Android reboot (reboot requires Android device-owner enrollment) and remotely configure the event theme, welcome message, idle timeout, available photo counts, and paired printer. Commands and settings take effect at the booth's next check-in. Location sharing is off by default; enable it locally in Admin settings, turn on Android Location, and grant while-in-use permission. The app reports on activation, about every 15 seconds while open and online, and immediately when Bluetooth adapter status or ESP32 connection changes. Dashboard data refreshes every five seconds and considers a booth offline after 90 seconds without a report, allowing more time for delayed Android/network check-ins. In Admin settings, use **Check Fleet connection now** to see whether the report was accepted or the HTTP error code returned by the server. Select a booth to see its first/last report, printer, kiosk, battery/storage, location, and individual sales and transaction totals. The booth continues operating when offline, but fleet status and pending commands will remain stale until its next successful report. A copied activation license could be replayed to falsify telemetry, so treat fleet data as operational monitoring, not independently audited accounting.

To deploy the online system when ready, use the setup steps in [FLEET_DEPLOYMENT.txt](hostinger/photobooth/FLEET_DEPLOYMENT.txt). They cover creating a MySQL database/user, importing the schema with phpMyAdmin, configuring credentials privately, uploading PHP files, and onboarding booths. Re-import the updated schema to create the remote-settings and command tables. The online dashboard requires HTTPS, PHP 8.1 or newer with PDO MySQL and Sodium, and the shared activation-code configuration.

### Checking for app updates

The app checks the built-in public update manifest when it starts, every six hours while running, and immediately whenever it returns to the foreground, including after returning from the APK installer. A successful check clears the update notice when the installed build matches or exceeds the published version. If a newer build is published, an animated black notice with **UPDATE NOW** and **LATER** appears on the idle home screen. **LATER** hides that version's notice until a newer release is published; **UPDATE NOW** opens the APK link. The admin can also open **App updates** in settings and tap **Check for updates** to compare the manifest's `versionCode` with the installed app; the result shows both build codes so it is clear if the manifest was not advanced. If using Google Drive, its page may first require tapping **Download** or **Download anyway** before opening the downloaded APK. Android still asks the device owner to allow installation from that source and confirm installation; this feature does not silently install or update the app. The app needs internet access to check the manifest.

The built-in manifest is the public Gist at `https://gist.githubusercontent.com/markycodes/fc8a1509d41f148abc88c8313e8e8b53/raw/update.json`. Edit that Gist when publishing a release. Its `apkUrl` must contain the real HTTPS APK download link before customers use the update checker.

Example `update.json`:

```json
{
  "version": "1.0.2",
  "versionCode": 3,
  "apkUrl": "https://example.com/photobooth/app-release.apk",
  "releaseNotes": "Bug fixes and new frame designs"
}
```

For every release, increase the build number after `+` in `pubspec.yaml`, build the APK, upload that exact APK, then update the public manifest's `versionCode` and `apkUrl` to match it. Changing `pubspec.yaml` alone does not publish an update. This source is build 154; advance the public manifest to 154 only after uploading this build-154 APK. Build 142 added compact signed activation codes while retaining support for existing codes; build 143 fixes photo/GIF upload authorization and fleet telemetry validation for compact codes; build 144 moves successful-payment notices to the top of the screen and animates the film-tape background; build 145 adds an admin-controlled rent mode that skips customer payment and enables session start after photo selection without displaying a rent label on the customer screen; build 146 keeps built-in photo-border artwork visible on all four sides after photos are cropped into their layout slots; build 147 fixes preview generation for photo-count-page selections of uploaded frames and preserves the aspect ratio of tall, phone-uploaded frames; build 148 increased film-tape background visibility; build 149 keeps the tape paths fixed while continuously scrolling the frame cells and sprocket holes along each strip on a five-second loop; build 150 shows the enabled live-wallpaper screen after one minute on the idle screen instead of ten minutes; build 151 mutes live-wallpaper video playback; build 152 points app upload, payment, and fleet services to snaplabbooth.com; build 153 reports fleet status every 15 seconds and refreshes the dashboard every five seconds; build 154 immediately reports Bluetooth/ESP32 state changes and marks stale ESP32 status as unknown. The user-facing version before `+` may be reset independently; Android uses the build number to determine whether an APK is an update. Keep the package ID and signing key unchanged; Android will reject an update signed with a different key. **This project's current release build uses the debug signing key** (`android/app/build.gradle.kts`), so it is suitable only for installs updated from builds signed with that same local debug key. Set up and securely back up a permanent release signing key before distributing production updates. With kiosk Lock Task Mode enabled, an admin may need to exit kiosk mode before opening the browser and Android installer.

### Photo borders and printing

Tall thermal-printer images are split into consecutive ESC/POS raster bands of at most 255 rows. This avoids truncation on printers with limited raster-height support and prevents remaining image bytes from being interpreted as text.

After admin sign-in, choose **Photo border** to pick from Classic, Party, Elegant, Christmas, Valentine's Day, Halloween, New Year, Birthday, Wedding, Easter, Summer, Graduation, Mother's Day, Lunar New Year, Diwali, Baby Shower, and Anniversary designs, or choose **No border**. With **No border**, customers can choose the photo-layout border color from the palette in the editor; the selection is applied to the print margin and the outline around each photo. The seasonal designs are drawn onto each captured shot. Admins can also import a custom PNG border; use a transparent center so the captured photo shows through. Oversized imported PNGs are safely resized to at most 1000 × 1500 pixels while preserving their original aspect ratio, before storage and frame analysis, to reduce memory use on tablets. If Android restarts the booth while the system file picker is open, the selected customer frame is recovered and Admin reopens with the frame ready to save. Custom borders are fitted to each final photo window after cropping, so the complete border remains visible and the editor no longer adds its dark outline around custom-bordered shots. Generated layouts use the SnapLab logo instead of a text heading. The launcher icon uses the supplied SnapLab camera artwork. The capture date (`MM/DD/YYYY`) is printed in a separate footer below the finished layout, so it does not cover frame artwork; it is included in the saved, uploaded, and printed image. Finished layouts are saved as PNG images in `Pictures/Photobooth`.

The booth follows all sensor-supported screen orientations. During sessions with more than two photos, each captured shot appears as a small thumbnail at the right-center of the camera preview. During the countdown, booth controls are hidden and only the large countdown number appears centered over the camera preview, without a circle or background. Captured photos are filtered and bordered concurrently to reduce processing time. Once the finished photo preview appears, a blinking QR button is visible immediately while the photo and GIF upload one at a time; each QR appears as soon as its own upload completes, and an open QR dialog updates automatically. If an online link is unavailable, it reports that the photo remains saved locally. After a photo is saved, its preview includes a **START OVER** button to return to the booth home immediately; otherwise, it returns home automatically after the configured preview duration.

Customers first choose 1–5 photos. Coin-slot sessions cost the adjustable price configured in Admin (default **₱20**), regardless of photo count or layout; PayMongo QR Ph charges the separate amount set in Admin (₱1–₱100,000). The booth waits for the same number of ESP32 credits as the configured whole-peso coin price, so the controller must map credits to that price at 1 credit per peso. Customer face-mask selection and preview are currently disabled. After payment is accepted, the customer taps the animated **START PHOTO SESSION** button to begin the countdowns. After capture, a two-step editor lets customers choose a **Photo strip** or **Collage** and then a frame before proceeding to filters and mirroring. Every frame template prints the configured SnapLab logo at the top; the logo header is also shown in the editor preview, with the frame artwork and photo openings kept together below it. Eleven frame designs are bundled in the app: Snoopy has one photo window; Classical Music, Memories, Green Polaroid, and Blue and Beige have three each; Cream and Maroon, Newsprint, Golden Film, Silver Wedding, and Film Negative have four each; Beige Collage holds five. Only frames matching the captured photo count are shown; bundled frames place each photo into its designed window, including the tilted, full-window photos in Green Polaroid. The full selected composition is fitted inside the editor preview without stretching, and frame thumbnails scale to show the complete artwork without cropping. Admin-imported customer PNG frames are analyzed for 1–5 enclosed transparent photo openings; each detected opening becomes a photo slot, the frame is shown only for matching photo counts, and photos are automatically fitted into those slots. Use one separate transparent opening per photo. On tablet-sized displays (480 logical pixels or more on the shortest side), the customization editor keeps the preview and controls side by side in both orientations. Single-column layouts automatically get a narrower preview area so tall frames do not sit in an unnecessarily wide panel; multi-column layouts retain a wider preview. Smaller displays stack controls below the preview. Frames are shown in a vertical list. To reposition a photo within its frame, touch and drag that photo directly; the PHOTO selector buttons are not shown. The mirror switch sits below the photo preview. In the second step, **FILTERS** and **DECORATIONS** switch between filter choices and decoration tools so they are not shown at the same time. Customers can drag decorations around the photo, use size controls or a two-finger pinch to resize them without an upper size limit, and rotate them with a two-finger twist. Admin-uploaded PNG and WebP decorations appear alongside the built-in choices and are included in the exported image. After choosing **USE THIS PHOTO**, the app renders and shows the exact full-quality image, including the decorations, that will be saved and printed. Customers can go back to adjust it or choose **CONFIRM EXACT PHOTO**; the confirmed image file is the one passed on for saving, uploading, and printing. Mirroring flips the captured photos while keeping the frame and its text readable. A camera shutter sound plays at each capture using Android's built-in camera sound. The Cartoon look is an offline posterized/outlined effect, not generative AI or a 3D-cartoon model. After a successful online upload, the preview shows a blinking soft-copy prompt in the top-right; tapping it opens the QR code.

Face-mask detection, mask uploads, and customer mask previews have been removed from the app.

Paid AI photo styles support all session sizes from one to five photos. A single coin or QR PH payment converts every photo in the current session, and Admin can set a separate AI conversion price for each photo count. The selected count's price is displayed before payment and charged once for the complete conversion. AI style prompts are defined in `hostinger/photobooth/pb_cartoon.php`; upload that updated file to the Hostinger document root for changes to take effect. All generated styles preserve each eye's source state independently: open eyes stay open, and an eye is drawn closed, winking, or squinting only when it has that state in the original. Pencil Sketch redraws the person and existing background as graphite while preserving the source scale, pose, and framing. Chibi converts the actual person’s visible head, face, body, hair, clothes, and accessories into a cute oversized-head, compact-body illustrated style, while preserving the original pose and background layout without adding characters or watermarks.

Event themes scatter softly shaded, theme-matched artwork across the booth background in both portrait and landscape, with subtle drifting and breathing animation; the Classic theme layers camera motifs with its film-tape animation. Upload a custom image under **Booth Logo** to replace the default logo on the idle home and customer photo-count screens; use **Use default** to restore it. Photo output is converted to a 576-dot-wide monochrome ESC/POS image with Floyd–Steinberg dithering to retain more facial detail and smooth tones than a single hard black/white threshold. The app uses Bluetooth Classic SPP and paced data chunks. Thermal receipt printers cannot reproduce color or the fine detail of dye-sublimation photo printers, and paper quality, printhead condition, darkness/heat settings and model-specific width affect the result. Check the exact printer's supported width and use **Print test page** before customer use. The admin diagnostics and local dashboard report battery, available storage, camera/ESP32 state, voice status, and recent printer test/print results. A Bluetooth printer that does not expose the standard SPP serial service or accept ESC/POS bitmap commands will need its vendor protocol.

The admin **Loop idle video** switch controls whether the video repeats or plays once and holds its final frame. When a video is selected, it plays over the uploaded image; the image remains visible if video playback fails. The app continues checking BLE credits while idle and only consumes credits after a customer chooses a photo count. The customer page returns to the idle home after 30 seconds without touch activity.

Printing uses monochrome, dithered ESC/POS 24-dot bitmap data over Bluetooth SPP; full-color printing is not supported by this generic path. Printer models can vary in their bitmap-command compatibility and supported dot width. ## Offline device activation

The booth is locked until a device-specific activation code is entered. Activation works completely offline and requires no Firebase account, paid plan, or internet connection. Each activation code is cryptographically signed for the Android device ID shown on the activation screen. New activation codes can separately entitle PayMongo QR Ph, Ganap QR Ph, both, or neither; payment providers are not enabled for every installation by default. Older activation codes remain valid for booth activation but do not grant either payment entitlement.

The app contains only the public verification key. The matching private signing key is stored on the owner's computer at `%LOCALAPPDATA%\PhotoboothKiosk\activation-private.json`; never share it or include it in an APK. Back it up securely. Losing it prevents issuing more codes for this app build.

### Time-limited trial activations

To create a trial code in PowerShell, choose its duration when issuing it:

```powershell
$key = Join-Path $env:LOCALAPPDATA 'PhotoboothKiosk\activation-private.json'
dart run tool/activation_code.dart issue-trial $key ANDROID_DEVICE_ID 30m
```

Replace `ANDROID_DEVICE_ID` with the ID shown on the booth's activation screen. Use a number followed by `m` for minutes, `h` for hours, or `d` for days, for example `30m`, `2h`, or `14d`. A bare number such as `14` continues to mean days. Durations range from 1 minute to 365 days. The trial countdown starts when you generate the code; the output includes its exact expiration date. Trial activations allow coin-slot sessions but do not grant PayMongo or Ganap QR payment. The booth returns to its activation screen when the trial expires, including if it remains open across the expiration or is restarted. Entering a new trial code requires a newly generated code. Build 155 or newer is required; existing permanent activations continue to work. The device clock must be set correctly.

To issue a code for a customer's device, add only the payment provider(s) you want to license to that device:

```powershell
$key = Join-Path $env:LOCALAPPDATA 'PhotoboothKiosk\activation-private.json'
flutter pub get
dart run tool/activation_code.dart issue $key ANDROID_DEVICE_ID --paymongo
```

Replace `ANDROID_DEVICE_ID` with the ID displayed in the app. Use `--paymongo` for PayMongo only, `--ganap` for Ganap only, both options for both, or omit both options for no QR payment entitlements. The command creates an 88-character compact signed code. Install build 142 or newer before entering a new permanent compact code; earlier builds do not recognize this format. Updating the app does not deactivate a device or replace its saved activation: existing v1 and v2 activation codes remain supported. Give the generated code to the customer to paste into the updated activation screen. On already activated devices, an admin can open **Update activation features** in settings and enter a replacement code issued for that same device. Only provider sections included in that device's signed activation are shown in Admin; the payment servers independently enforce the same entitlements. A provider still needs to be enabled in Admin and configured on the server; device entitlement alone does not turn on a payment provider globally. Ganap remains unavailable until its minimum charge supports this booth's fixed ₱20 session price. Permanent codes stay valid on that device and are rechecked locally on every app start. Factory-resetting the device may change its Android ID, requiring a new code.

Upload the updated `ganap_common.php`, `pb_auth.php`, `ganap_checkout.php`, `ganap_status.php`, `paymongo_checkout.php`, and `paymongo_status.php` to Hostinger so the server accepts compact signed licenses and rejects checkout/status requests from devices without the matching entitlement. Keep the same owner private signing key and public key; generating a different key invalidates existing activation codes.

To generate a new owner keypair, run `dart run tool/activation_code.dart keygen <private-key-file>` and replace `activationPublicKeyHex` in `lib/device_activation.dart` with the printed public key **before building/distributing the app**. A new keypair invalidates codes made for previous app builds. This is a practical license gate, not tamper-proof DRM: a sufficiently modified APK can remove client-side checks.

## Lock the tablet to the booth

Android only allows an app to fully disable app switching and system navigation when it is allowlisted for Lock Task Mode by a device-owner app. There is no ADB command that can force device-owner mode on every Android model: provisioning is generally rejected after accounts have been added, when another owner/profile owner exists, or when an OEM disables ADB provisioning. Provision a new or factory-reset tablet before normal setup.

1. Install the current APK on the tablet and launch it once. The APK must register `KioskDeviceAdminReceiver`; build 156 or newer does so. The helper checks this receiver before attempting provisioning.
2. Enable Developer options and USB debugging, connect the tablet, unlock it, then accept the computer's USB debugging prompt. Download and extract Android SDK Platform-Tools if needed.
3. From the project folder, run the helper. It searches `PATH` and the default Android SDK location, or prompts you for the Platform-Tools folder:

   ```powershell
   .\tool\set-device-owner.ps1
   ```

   To specify the folder where you extracted Platform-Tools:

   ```powershell
   .\tool\set-device-owner.ps1 -AdbPath "$env:USERPROFILE\Downloads\platform-tools"
   ```

   If more than one device is connected, select one using `-Serial DEVICE_SERIAL`. The helper checks the ADB connection and app installation and asks for confirmation before provisioning. It cannot override Android or manufacturer restrictions. If PowerShell blocks the script, run `Set-ExecutionPolicy -Scope Process Bypass` in that same PowerShell window, then retry.

4. Open Photobooth and confirm the header says **Kiosk mode active**. This status means Android reports the activity is actually in Lock Task Mode, not merely allowlisted.

If Android rejects the command, factory-reset only if you have backed up the device and are prepared to configure it again. Some manufacturers require their enterprise/dedicated-device enrollment flow and do not permit ADB-based provisioning. Without device-owner permission, Android's screen-pinning fallback is available on supported devices, but it cannot reliably disable all system navigation.

The app starts or reasserts Android Lock Task Mode whenever its activity resumes, sets itself as the persistent Home app, and hides system navigation affordances. It will return to the booth after a restart. After admin authentication, **Log out and exit kiosk mode** unlocks system navigation and app switching; use the same three-tap camera-icon gesture and password to re-enable kiosk mode. Android Lock Task Mode restricts app switching and system navigation, but cannot prevent physical power-button use or guarantee protection from manufacturer-specific emergency/recovery controls.

Before opening the booth for customers:

1. Verify **Kiosk mode active** is shown after a cold restart.
2. Test the Home, Recents, and edge-swipe gestures on the exact tablet model; the booth should remain locked in the app.
3. Test camera, BLE, photo saving, and power recovery while still in kiosk mode.
4. Keep the tablet's data backed up and document a tested service/recovery process for that model. Removing device-owner management may require an authorized factory reset; do not deploy until the owner understands and has tested the recovery process.

The kiosk exit control is only available after admin authentication.

## ESP32 coin-slot setup

Flash `esp32/PhotoboothCoinServer.ino` to the ESP32 installed on the JUANKIOSK board using the ESP32 Arduino core and ArduinoJson library. This replaces the firmware currently on the ESP32, including its **YowToBooth-8634** BLE service and any other functions provided by that firmware. No Wi-Fi credentials are required. The sketch advertises as **Photobooth ESP32**; the Android app scans for the service UUID below and connects automatically.

The JUANKIOSK board is labeled `CoinSlot in = P15` with `Trigger Type = High`; the sketch therefore counts rising-edge pulses on ESP32 GPIO 15. Keep the ESP32 installed in the JUANKIOSK socket rows so it receives the board's coin signal. Do not connect a higher-voltage coin acceptor output directly to an ESP32 GPIO; verify that the JUANKIOSK signal is 3.3 V-safe before operating. The example sketch keeps credits in RAM, so power loss resets them; use nonvolatile storage if balances must survive a restart.

### Smart charging recreation

`esp32/PhotoboothSmartChargeServer/PhotoboothSmartChargeServer.ino` is a separate Arduino sketch that preserves coin credits and adds smart charging. Defaults are 20% start and 90% stop; admins can customize both values in the app settings (start must be lower than stop). The app reports tablet battery and both thresholds over the existing BLE characteristic every 30 seconds. Between thresholds the ESP32 retains its previous charge state; a missing/stale report turns the charger output off. Bill-acceptor RS232 and the configurable timer GPIO are not implemented.

For the board revision currently being tested, charging started when the D32 header pin was touched, so the smart-charging sketch uses ESP32 GPIO 32 as an observed candidate control pin, active-high. It drives GPIO 32 HIGH to enable the onboard SMART CHARGING USB-A output and LOW to disable it. This observation is not a confirmed schematic/pinout: do not touch or short header pins while powered, and verify the mapping with the board vendor or a qualified technician. Connect the tablet to the board's SMART CHARGING USB-A port; do not connect USB power to an ESP32 GPIO. The output is kept off until a valid battery report arrives. The sketch replaces the firmware currently on the ESP32, including any other board firmware functionality.

### BLE GATT protocol

The app and both example sketches use this service and characteristic:

- Service: `6f3a1000-9d7b-4c2a-8e51-13b7c0a10000`
- Credit characteristic: `6f3a1001-9d7b-4c2a-8e51-13b7c0a10000` (read and write)

Write a UTF-8 JSON request to the characteristic, then read the characteristic for its JSON response:

- Read credits: write `{"op":"credits"}` → read `{"credits":3,"consumed":false}`
- Spend credits: write `{"op":"consume","amount":2}` → read `{"credits":1,"consumed":true}`
- Insufficient balance: response includes `"consumed":false` and the unchanged `"credits"` balance.
- Report tablet battery and thresholds: write `{"op":"battery","percent":42,"startPercent":20,"stopPercent":90}` → read the usual credit response; battery and thresholds must be valid percentages and start must be lower than stop.

Only `PhotoboothSmartChargeServer.ino` supports the battery operation; `PhotoboothCoinServer.ino` supports credits and consume only. The ESP32 is authoritative for the balance and deducts credits atomically. The app polls the ESP32 over BLE and consumes the configured coin-slot price in credits for each paid session, regardless of the selected photo count or layout.
